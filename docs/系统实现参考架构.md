# edge-service-sdk 系统实现参考架构

本文档基于当前 `edge-service-sdk` 的目录与实现整理，目标不是描述某一个具体协议项目，而是沉淀一套适用于 S7、Fanuc、Modbus、三菱、欧姆龙等边缘采集服务的统一运行时参考架构。

本文档适用对象：

- 新协议驱动项目的架构设计者
- 需要把当前 runtime 能力迁移到其它协议项目的开发者
- 需要定义目录、边界、配置、控制链路与验收标准的负责人

本文档重点回答：

- 哪些能力应沉淀为统一 runtime 骨架
- 哪些能力必须留在协议驱动里
- 新项目目录怎么组织
- HTTP / MQTT / 控制任务链路怎么统一
- 命令、属性、查询、状态、遥测应分别落在哪些模块
- 新驱动项目落地时应该做哪些事

如果你关心的是：

- 仓库入口和公共能力总览
  看 `README.md`
- 具体协议项目怎么接线
  看对应协议项目的 `readme.md` 与 `configs/*.yaml`
- MQTT 连接状态机、健康检查、可靠队列设计
  看协议项目中的 MQTT 设计文档与 SDK `transport/mqtt`、`telemetry/reliable`

## 1. SDK 定位与边界

`edge-service-sdk` 的目标是统一“运行时”，而不是统一“协议驱动”。

统一到 SDK 的能力包括：

- 配置加载、profile 合并、运行时规范化
- Auth bootstrap、token 签发、鉴权与凭据查询
- 设备状态跟踪与运行态输出
- Telemetry 事件模型与 Trace 语义
- MQTT 连接管理、发布、订阅、恢复与健康检查
- Telemetry 离线缓存、SQLite 落盘、重放与统计
- Property / Command 的 HTTP 与 MQTT 控制闭环
- Control Job 与 Result 的持久化、查询、导出、诊断
- Runtime HTTP 运维接口
- Worker 监督与依赖检查

必须保留在协议项目内的能力包括：

- 协议地址解析
- 设备连接与底层通信库
- 读写命令的具体执行
- 协议值类型转换与厂商差异处理
- 设备发现、厂商特定异常与重试策略中的协议特例

原则：

- 不要求一个服务兼容所有 PLC 协议
- 不同协议保持独立驱动实现
- Runtime 骨架尽量统一
- 采集、投递、自恢复、配置模型、控制结果语义尽量统一

## 2. 当前仓库的核心分层

推荐把当前 SDK 理解为 6 层：

```text
Protocol Driver
  -> Device SDK Catalog
  -> Property / Command Runtime
  -> Control Store + Query Layer
  -> MQTT + Reliable Queue
  -> HTTP Ops + Auth
```

### 2.1 Protocol Driver 层

对应协议项目中的驱动实现，职责是：

- 建立设备连接
- 执行读写
- 处理地址解析
- 输出统一 `CommandValue` / `AsyncValues`
- 处理协议值类型、缩放、精度等细节

这层不应承担：

- MQTT topic 生命周期
- SQLite 缓存与结果持久化
- HTTP 接口实现
- Control Job 管理
- 通用命令注册框架

### 2.2 Device SDK Catalog 层

SDK 在 `runtime/app` 中把设备配置、产品分组和状态跟踪包装为 `DeviceSDK`，提供统一目录能力：

- `DeviceConfigByName`
- `DevicesByProductCode`
- `ProductCodes`
- `AsyncValuesChannel`
- 设备连接/读写状态回调

这层的作用是把“配置目录”和“驱动回调”统一成运行时可复用接口，供 property / command / query / status 等模块共用。

### 2.3 Property / Command Runtime 层

当前 SDK 已将控制链路拆成两个独立 runtime：

- `runtime/property`
- `runtime/command`

`runtime/property` 负责：

- HTTP `property/get` / `property/set`
- MQTT `property/get` / `property/set` 订阅处理
- `property/result` 发布
- `property/report` 自动上报
- Property 任务入库、结果记录、进度与失败上下文输出
- 重启后恢复未完成 property 任务

`runtime/command` 负责：

- Command Registry 的接入与校验
- HTTP `command/call/:identifier`
- MQTT `command/call/{identifier}` 订阅处理
- 同步/异步命令执行
- `command/result` 发布
- 异步命令状态跟踪、进度记录与重启恢复

两个 runtime 的共同原则：

- 请求统一携带 `trace_id`
- 结果统一落到 control store
- MQTT 与 HTTP 共用同一套结果模型
- 同一条控制链路允许同步返回、异步完成和重启后恢复

### 2.4 Control Store + Query 层

这是 v0.6.5 起最重要的新骨架之一，对应：

- `control`
- `runtime/control`
- `runtime/app/control_query.go`
- `runtime/app/mqtt_query.go`

职责包括：

- 保存控制任务（job）
- 保存过程态与终态结果（result）
- 记录 pending property / pending command
- 提供按 `trace_id` 查询结果的统一入口
- 提供任务列表、诊断、事件时间线、导出能力
- 支撑 HTTP 查询接口和 MQTT query request/reply 查询接口

统一结果骨架：

```json
{
  "trace_id": "req_xxx",
  "code": 0,
  "message": "success",
  "time": 1712822035000,
  "data": {}
}
```

控制层的价值在于：

- HTTP 与 MQTT 不再各自维护一套结果状态
- UI / 平台 / 联调工具都按 `trace_id` 查询同一份事实
- 进程重启后仍可恢复 pending 任务并保留结果历史

### 2.5 MQTT + Reliable Queue 层

对应：

- `transport/mqtt`
- `telemetry`
- `telemetry/reliable`

职责：

- MQTT 显式建连、断连、重连、健康检查、重订阅
- Telemetry / PropertyResult / PropertyReport / CommandResult / StatusReport 发布
- Telemetry 统一事件模型、时间语义与 trace 生成
- SQLite 离线缓存、批量刷盘、周期性重放、ACK 删除、限流与统计
- 注册 MQTT property / command / query handlers

边界：

- MQTT 层负责 topic 生命周期与消息收发，不负责协议驱动执行
- Reliable queue 主要兜底 telemetry 重放，不替代控制结果存储
- `propertyReport` 与 `propertyResult`、`commandResult` 严禁混用

### 2.6 HTTP Ops + Auth 层

对应：

- `auth`
- `ops/http`
- `ops/status`

职责：

- 健康检查、ready 检查、运行态总览
- Auth bootstrap/init、token 签发、credential query
- Device model query：properties / telemetry / commands / command input / output
- Control query：property result、command result、job list、job export、job diagnostics、job timeline
- 设备状态快照输出

HTTP 服务必须与采集、投递、控制主链路解耦：

- HTTP 失败不应阻塞 telemetry worker
- HTTP 服务运行在独立协程
- readiness 至少检查 auth、MQTT、核心 runtime 依赖

## 3. 推荐的目录参考

一个新的协议项目推荐保持如下结构：

```text
cmd/service/main.go
configs/config.yaml
devices/*.yaml
profiles/*.yaml
internal/driver/<protocol>/...
internal/commands/...
```

其中：

- 协议项目本地目录只保留协议驱动、命令实现、厂商依赖和少量项目定制
- 公共 runtime 直接从 SDK 引入，不要复制到协议项目内部

SDK 自身建议按如下职责理解：

```text
config/               配置模型、加载、合并、兼容辅助
command/              命令注册、描述、上下文、错误模型
control/              控制请求/结果公共模型
auth/                 bootstrap / token / 鉴权
ops/http/             HTTP 运维与控制接口
ops/status/           设备状态追踪
runtime/app/          Bootstrap 组装与 MQTT 查询装配
runtime/property/     属性控制与自动上报
runtime/command/      命令执行与异步恢复
runtime/control/      SQLite 控制存储与诊断
runtime/dependency/   依赖检查
runtime/scheduler/    Worker 监督
telemetry/            标准 telemetry 事件
telemetry/reliable/   可靠队列与重放
transport/mqtt/       MQTT 生命周期与发布/订阅
```

## 4. 启动与运行链路

当前 `runtime/app.Bootstrap(...)` 的主流程可以概括为：

1. 加载并规范化配置
2. 初始化 logger
3. 校验设备声明的 command 与 registry 是否一致
4. 初始化 MQTT publisher
5. 初始化 reliable dispatcher
6. 初始化 status tracker
7. 初始化 auth service
8. 构建 `DeviceSDK`
9. 初始化协议 driver
10. 执行依赖检查
11. 初始化 control store
12. 初始化 property runtime，并恢复 pending property
13. 初始化 command runtime，并恢复 pending command
14. 初始化 MQTT query service
15. 安装 status publisher
16. 启动 telemetry 异步处理
17. 启动 HTTP runtime server
18. 启动协议 worker，并交给 supervisor 监督

这个流程背后的关键设计是：

- 配置、Auth、MQTT、Control Store、HTTP、Driver 都由统一 bootstrap 组装
- 协议项目本身只需提供 driver 和可选 command registry
- Property / Command / Query 都复用同一份设备目录和结果存储

## 5. HTTP / MQTT / 控制闭环参考

### 5.1 属性控制

属性链路同时支持：

- HTTP 发起：`/api/v1/device/control/property/get`、`/property/set`
- MQTT 发起：`v1/iot/{productCode}/property/get`、`/property/set`
- 结果查询：`/api/v1/device/control/property/result/:trace_id`
- 设备主动结果：`v1/iot/{productCode}/property/result`
- 设备自动事实值：`v1/iot/{productCode}/property/report`

规则：

- `property/report` 只做事实值上报，不做控制结果
- 控制结果统一按 `trace_id` 查询
- 结果可先返回过程态，后续再入库终态

### 5.2 命令控制

命令链路同时支持：

- HTTP 发起：`/api/v1/device/control/command/call/:identifier`
- MQTT 发起：`v1/iot/{productCode}/command/call/{identifier}`
- 结果查询：`/api/v1/device/control/command/result/:trace_id`
- 任务诊断：`/api/v1/device/control/jobs`、`/jobs/export`、`/jobs/diagnostics`
- 设备主动结果：`v1/iot/{productCode}/command/result`

规则：

- `identifier` 从 topic / URL 获取，不放进 body
- 支持同步命令和异步命令
- 异步命令可上报进度，并在重启后继续恢复

### 5.3 查询链路

当前 SDK 已支持两类查询：

- HTTP query
  - 模型查询
  - 控制任务查询
  - 控制结果查询
- MQTT query
  - 面向设备模型、命令列表、命令输入输出、控制任务与结果的 request/reply 查询

适用场景：

- 平台侧通过 HTTP 给 UI 提供稳定接口
- 联调工具或设备侧代理通过 MQTT 做轻量查询

### 5.4 遥测与状态

遥测与状态的职责要与控制链路分离：

- 遥测：连续采样、趋势数据、规则引擎输入
- 状态：连接状态、运行状态、健康状态、最近读写情况
- 控制结果：属性/命令的过程态与终态

不要把三类语义混在同一 topic 或同一结果表述中。

## 6. 新协议项目接入建议

接入一个新的协议项目时，建议按如下步骤落地：

1. 实现协议 driver，满足 SDK `driver.ProtocolDriver` 接口
2. 准备 `configs/config.yaml`、`devices/*.yaml`、`profiles/*.yaml`
3. 如需命令能力，实现命令并注册到 `command.Registry`
4. 调用 `runtime/app.Bootstrap(serviceName, version, driver, registry)`
5. 确认 HTTP health/ready/runtime/status 正常
6. 确认 MQTT telemetry/property/status/command topics 正常
7. 验证 property 与 command 的 HTTP / MQTT / trace 查询闭环
8. 验证服务重启后 pending property / command 能恢复
9. 验证 telemetry 离线缓存与重放能力

## 7. 架构验收标准

一个基于 SDK 的协议项目，至少应满足以下验收标准：

- 能通过统一 bootstrap 启动
- 能输出统一 health / ready / runtime/status
- 能复用统一 auth 机制
- 能发布 telemetry 与 status
- 能通过 HTTP 与 MQTT 处理 property / command
- 能按 `trace_id` 查询控制结果
- 能在重启后恢复未完成控制任务
- 能复用统一 reliable queue，而不是自行实现离线缓存
- 协议项目目录内不重复复制 SDK 的 HTTP/MQTT/control/runtime 代码

## 8. 版本说明

截至当前文档版本，本文档对应 `edge-service-sdk v0.6.5`。

后续若继续扩展事件通知、批量控制、更多 MQTT query 视图或多租户凭据能力，应优先扩展 SDK runtime，而不是在单个协议项目里先行分叉实现。
